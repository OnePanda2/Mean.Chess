# Online protocol and game lifecycle (Phase 2, Track A)

**Status: approved by the founder on 8 October 2026. Nothing here is built yet.**
This is the contract between the browser and the game server. The types become
`src/online/protocol.ts`, shared by both sides. Architecture: [ONLINE-ARCHITECTURE.md](ONLINE-ARCHITECTURE.md).
Storage: [ONLINE-DATA-MODEL.md](ONLINE-DATA-MODEL.md). Sources: [PHASE-2-SOURCES.md](PHASE-2-SOURCES.md).

---

## 1. Principles

1. **The server is the only authority.** The client sends *intents* (a move, an offer, a
   resignation). The server decides, using the shared engine, and the client displays what the server
   accepted. A client never reports a position, a legality verdict or a result.
2. **Same engine on both ends.** The client checks moves locally for instant feedback, but only a
   server event changes the game. The server sends moves, never positions to trust. Each `moved` event
   carries the MeanFEN after the move, so a client whose engine disagrees notices at once.
3. **Every state change has a revision.** `rev` orders events. `ply` (the number of moves played) is
   the precondition for a move. `mid` makes a move idempotent.
4. **Reconnecting is normal.** Any socket can drop at any time, and every deploy drops all of them
   [S4]. The answer to a reconnect is always a full snapshot, at most ~2 KB [M1].
5. **Nothing reveals the Kill Zone.** The server sends no analysis, threats or hints. A royal capture
   reaches the opponent as an ordinary move whose `result` ends the game (D-39, D-46).

## 2. Identifiers

| Thing | Format | Entropy | Where it lives |
|---|---|---|---|
| Game id | 10 characters of Crockford base32 (`0-9 A-Z` minus `I L O U`), generated by the server from `crypto.getRandomValues`. Shown as `7KQ2M-X9FTA`. Input is upper-cased, spaces and hyphens are dropped, `O`→`0`, `I`/`L`→`1`. | 50 bits | URL (`/online/?g=7KQ2MX9FTA`), the Durable Object's name |
| Seat token | 32 random bytes, base64url (43 characters), generated by the server | 256 bits | The player's `localStorage` (`mean-chess:online:v1:<gameId>`); the server stores only its SHA-256 |
| Move id (`mid`) | 12 random base64url characters, generated by the client per move attempt | 72 bits | In flight; stored next to the move |
| Join nonce | 16 random base64url characters, generated by the client per join attempt | 96 bits | `sessionStorage` until the join succeeds |

The invite link is the game's permanent address. Who opens it decides what they see:
- a holder of a seat token resumes the game;
- anyone else gets the join screen while a seat is open, "this game is between two other players"
  while it's being played, and the finished game, read-only, for 30 days after it ends.

## 3. Lifecycle

```
            POST /v1/games
                 │
                 ▼
          ┌────────────┐  creator aborts            ┌──────────────────────────┐
          │  waiting   │ ─────────────────────────► │ finished: aborted        │
          │ 1 seat set │  no join within 24 h       │ (deleted after 30 days)  │
          └─────┬──────┘ ─────────────► expired → deleted at once
                │ POST /join claims the 2nd seat
                ▼
          ┌────────────┐  move ends the game (royal, mate, stalemate, threefold, fifty-move)
          │   active   │  resign · draw agreed · abort (before each side has moved)
          │            │  claim (opponent absent ≥ 120 s) · 7 days idle → abandoned
          └─────┬──────┘  2,000 plies → move-limit draw
                ▼
          ┌────────────┐  rematch accepted → a NEW game (colours swapped, same seat tokens)
          │  finished  │  viewable read-only by link for 30 days, then deleted
          └────────────┘
```

| From | Event | To | Who | Notes |
|---|---|---|---|---|
| — | `POST /v1/games` | waiting | anyone (rate limited) | Creator chooses White, Black or random (default random) |
| waiting | `POST /v1/games/:id/join` | active | anyone with the link, after clicking **Join** | The page never joins by itself on load, so link previews and crawlers can't take the seat |
| waiting | `abort` from the creator | finished (aborted) | creator | "Cancel invite" |
| waiting | alarm at created + 24 h | expired, deleted | server | Unjoined rooms don't pile up |
| active | `move` that ends the game | finished | side to move | Result from the engine |
| active | `resign` | finished (resignation) | either player | The engine's `resign(game, loser)` |
| active | `draw-answer` accepting a pending offer | finished (agreement) | the player offered to | The engine's `agreeDraw` |
| active | `abort` while either side has yet to make a move (`ply < 2`) | finished (aborted) | either player | No winner |
| active | `claim` with the opponent absent ≥ 120 s | finished (claim-win or claim-draw) | the present player | Approved by the founder (F2) |
| active | alarm: 7 days with no move and no connection | finished (abandoned) | server | No winner. Approved (F2) |
| active | the 2,000th ply is played | finished (move-limit) | server | A draw. Keeps every game loadable (the saved-game limit). Approved (F2) |
| finished | `rematch-offer` + `rematch-answer` accept | new game, active | both players, both connected | Colours swap; the same seat tokens carry over, so nothing secret is re-sent |
| finished | alarm at finished + 30 days | deleted | server | |

## 4. HTTP API

Base URL: `VITE_ONLINE_URL` (production: `https://meanchess-online.<subdomain>.workers.dev`). All bodies
are JSON (`Content-Type: application/json`), at most 2 KB. Every response carries CORS headers for
allowed origins only.

| Method and path | Request | Success | Errors |
|---|---|---|---|
| `POST /v1/games` | `{"protocol":1,"rules":"0.1","color":"white"\|"black"\|"random"}` | `201 {"gameId","you":"white"\|"black","token","protocol","rules"}` | 400 `bad-request`, 403 `origin-not-allowed`, 409 `unsupported-protocol` / `rules-mismatch`, 429 `rate-limited` (+`Retry-After`), 503 `online-full` (the day's capacity is used up; the body includes `reopensAt`) or `unavailable` (kill switch) |
| `POST /v1/games/:id/join` | `{"protocol":1,"rules":"0.1","joinNonce":"…"}` | `200 {"gameId","you","token"}`. A retry with the same `joinNonce` returns the same seat with a fresh token, and the old one stops working. | 404 `not-found`, 409 `game-full`, 410 `game-over`, 429, 503 |
| `GET /v1/games/:id` | — | `200` with `status` and `creatorColor` while waiting; `status` only while active (no live spectating in v0.3); for a finished game, the SavedGame v1 record plus result and dates | 404 `not-found` (unknown, expired or deleted) |
| `GET /v1/games/:id/ws` | WebSocket upgrade. **No token in the URL.** | 101, then the WebSocket session (§5) | 400 (not an upgrade), 403 `origin-not-allowed`, 404, 429, 503 |
| `GET /v1/health` | — | `200 {"ok":true,"protocol":1,"rules":"0.1","build":"<git sha>"}` | — |
| `POST /v1/events` (approved, F6b; batched and sampled, P2-34) | `{"e":["tutorial-started"\|"tutorial-completed"\|"computer-game-started"\|"friend-game-started", …]}`: one request per page visit with that visit's events, sent by 1 visit in 4 | 204 | 400, 429 |

Error bodies are always `{"error":"<code>","errorId":"<8 chars, internal errors only>"}`. The page maps
codes to its own wording and never renders server text as HTML.

## 5. The WebSocket session

1. The page opens `wss://…/v1/games/<id>/ws`. The Worker checks `Upgrade`, `Origin` and the rate limit,
   then forwards to the game's object, which accepts the socket with the Hibernation API and tags it
   *unauthenticated*.
2. **The first message must be `hello`, within 10 s.** The object hashes the token and looks for a
   matching seat. On success it tags the socket with the seat (`serializeAttachment`, a few bytes
   [S4]), marks that seat present, and replies with `state`. On failure it sends `error` and closes the
   socket.
3. After that, messages flow both ways (§6, §7). Heartbeat: the client sends the literal text `ping`
   every 25 s. The runtime answers `pong` by auto-response without waking the object [S4]. If no `pong`
   arrives within 10 s, the client reconnects.
4. Limits:
   - at most 3 sockets per seat (a 4th closes the oldest, code 4409);
   - at most 4 unauthenticated sockets per game;
   - messages of 2,048 bytes at most (else close 1009);
   - text frames only;
   - a token bucket of 20 messages refilling at 5 per second (else close 1008).

| Close code | Meaning | Client reaction |
|---|---|---|
| 1000, 1001 | Normal, going away | Reconnect if the game is still open and the page is visible |
| 1006, 1011, 1012 | Abnormal, server error, restart (deploys) | Reconnect with backoff (§8) |
| 1008 | Policy (rate limit, abuse) | Show "Connection refused"; offer a manual retry after 30 s |
| 1009 | Message too large | Bug: report it and reload |
| 4401 | Not authenticated (bad or missing token) | Don't retry: show "You aren't a player in this game" |
| 4404 | Game not found | Don't retry |
| 4409 | Superseded by a newer connection from the same seat | Don't retry from this tab: "This game is open in another tab" |
| 4410 | Game deleted | Don't retry |
| 4426 | Client outdated | Show "Mean Chess was updated. Reload to keep playing" |

## 6. Client → server messages

Every message is a JSON object with a `t` field. Unknown fields are ignored. An unknown `t` is answered
with `rejected` (code `unknown-type`), and the socket stays open.

| `t` | Fields | Who may send | Preconditions | Effect | Idempotency |
|---|---|---|---|---|---|
| `hello` | `protocol` (int), `rules` (string), `token` (string, 43 chars) | anyone, first message only | protocol supported; rules equal to the game's | Authenticates the socket; replies `state` | Safe to repeat on a new socket |
| `move` | `ply` (int ≥ 0), `uci` (`^[a-h][1-8][a-h][1-8][qrbn]?$`), `mid` (`^[A-Za-z0-9_-]{8,24}$`) | a player | status active; sender is the side to move; `ply` = moves played; legal by `play()` | Appends the move; broadcasts `moved` | A repeat with a known `mid` from the same seat changes nothing: the sender gets that ply's `moved` again |
| `draw-offer` | — | a player | status active; no pending offer; fewer than 3 offers by this player; the opponent has moved since this player's last declined offer | Pending offer; broadcasts `draw` | A repeat while pending: rejected `already-offered` |
| `draw-answer` | `accept` (boolean) | the player offered to | an offer from the opponent is pending | Accept: game ends (agreement), `ended`. Decline: offer cleared, `draw` | No pending offer: rejected `no-offer` |
| `resign` | — | a player | status active | Game ends (resignation), `ended` | Game already over: `state`, no change |
| `abort` | — | creator while waiting; either player while `ply < 2` | as stated | Game ends (aborted), `ended` | Already over: `state` |
| `claim` | `outcome` (`"win"` or `"draw"`) | a player | status active; opponent absent ≥ 120 s (after a fresh liveness check, §8.3) | Game ends (claim-win or claim-draw), `ended` | Already over: `state` |
| `rematch-offer` | — | a player | status finished, not aborted or expired; no rematch created yet; fewer than 3 offers by this player; **both players connected**; the day's hard cap not reached | Pending rematch; broadcasts `rematch` | Pending already: rejected `already-offered`. At the hard cap: rejected `online-full`, and the page offers a game against the computer instead |
| `rematch-answer` | `accept` (boolean) | the player offered to | a rematch offer is pending and the offerer is still connected | Accept: creates the next game; broadcasts `rematch` with `next`. Decline: clears it | |
| `sync` | — | a player | — | Replies `state` (with a fresh liveness check of the opponent) | Always safe |
| `stats` | `rtt50`, `rtt95`, `reconnects` (non-negative ints, capped) | a player, once per game, after the end | status finished | Recorded as metrics only | Later ones ignored |
| `ping` (literal text) | — | anyone | — | Auto-response `pong`; the object doesn't wake | — |

**Draw offers.** An offer stands until the opponent answers it **or makes a move** (moving declines
it). Either player may offer at any time during an active game, three times per game at most.

## 7. Server → client events

**Revisions.** The room's revision, `rev`, increases by exactly 1 for every broadcast state change.
- The change events (`moved`, `presence`, `draw`, `ended`, `rematch`) carry the new `rev`.
- `state` and `rejected` carry the *current* `rev` for reference; they are replies, not changes.
- `error` and `pong` carry none.

```ts
type Seat = 'white' | 'black'
type EndReason =
  | 'royal-capture' | 'royal-slaughter' | 'checkmate'          // engine, decisive
  | 'stalemate' | 'threefold' | 'fifty-move'                   // engine, drawn
  | 'resignation' | 'agreement'                                // engine helpers
  | 'claim-win' | 'claim-draw' | 'aborted' | 'abandoned' | 'move-limit'  // online only (F2)
interface Result { winner: Seat | null; reason: EndReason }

// Full snapshot: after hello, after sync, and after a stale or duplicate command.
interface StateEvent {
  t: 'state'; rev: number; protocol: number; rules: string
  gameId: string; you: Seat
  status: 'waiting' | 'active' | 'finished'
  start: string                    // MeanFEN (the standard start in v0.3)
  moves: string[]                  // UCI, in order
  drawOffer: Seat | null
  rematch: { offeredBy: Seat | null; next: { gameId: string; you: Seat } | null }
  presence: { connected: Record<Seat, boolean>; absentSince: Record<Seat, number | null> }
  claimableAt: number | null       // server time when `you` may claim; null if not applicable
  result: Result | null
  serverTime: number               // epoch ms, for countdown offsets
}

type ServerEvent =
  | StateEvent
  | { t: 'moved'; rev: number; ply: number; uci: string; by: Seat; mid: string
      fen: string                  // MeanFEN after the move: the desync check
      result: Result | null }      // set when this move ended the game
  | { t: 'rejected'; rev: number; of: string; code: RejectCode; mid?: string }  // sender only
  | { t: 'presence'; rev: number; connected: Record<Seat, boolean>
      absentSince: Record<Seat, number | null>; serverTime: number }
  | { t: 'draw'; rev: number; offeredBy: Seat | null; declinedBy: Seat | null }
  | { t: 'ended'; rev: number; result: Result }                 // endings that are not moves
  | { t: 'rematch'; rev: number; offeredBy: Seat | null; declinedBy: Seat | null
      next: { gameId: string; you: Seat } | null }               // `you` is per recipient
  | { t: 'error'; code: ErrorCode; errorId?: string }           // connection-level, then close

type RejectCode = 'not-your-turn' | 'stale' | 'illegal-move' | 'game-over' | 'not-allowed'
  | 'already-offered' | 'no-offer' | 'offer-limit' | 'opponent-present' | 'opponent-offline'
  | 'bad-request' | 'unknown-type' | 'online-full'
type ErrorCode = 'unsupported-protocol' | 'rules-mismatch' | 'not-authenticated' | 'not-found'
  | 'game-deleted' | 'internal'
```

How the client applies events:
- **`state`:** always processed.
  1. Rebuild the game with `loadGame({format, version: 1, rules, start, moves, result: null})`. This is
     the existing saved-game loader, which replays and validates every move.
  2. Show `state.result` as the game's end. For on-board endings it always matches the engine's own
     outcome; the client checks this. Online-only endings (claim, abort and so on) exist only on the
     server.
  3. Set `lastRev = state.rev`.
  4. Reconcile any pending move (§8.2).
- **`rejected`:** always processed (it answers this client's own command). Roll back the pending
  command it names. On `stale`, a `state` follows.
- **`moved`:**
  1. Expect `ply === localMoves.length`; otherwise ask for `sync`.
  2. Play the move through the local engine and compare the resulting MeanFEN with `fen`.
  3. On a mismatch, report `desync` (a critical metric) and ask for `sync`.
  4. If `result` is set, show the end screen.
- **Gaps:** these rules apply to the change events only.
  - `rev ≤ lastRev`: a duplicate (for example the re-sent `moved` after a duplicate `mid`). Ignore it,
    except that a duplicate `moved` carrying this client's pending `mid` confirms the pending move.
  - `rev > lastRev + 1`: a gap. Ask for `sync`.
  - Otherwise apply it and set `lastRev = rev`.
- **Unknown events:** ignore unknown `t` values (forward compatibility).

## 8. Ordering, idempotency, races, reconnects

### 8.1 The guarantees and why they hold

| Guarantee | Mechanism |
|---|---|
| One authority per game, no split brain | One Durable Object per game id; every request for that id reaches the same single-threaded object [S19] |
| Commands are processed one at a time, atomically | Input gates hold new events while the handler runs [S5]. The move handler does all its work synchronously, with no `await`: validate, `play()`, two SQL writes, broadcast. |
| No client sees an unsaved move | Output gates hold outgoing messages until the writes are durable [S5] |
| No two moves for one turn | Seat check (sender = side to move) plus `ply` precondition, evaluated serially |
| No stale writes | `ply` must equal the number of moves played, or the command is rejected `stale` and the sender gets a fresh `state` |
| No duplicate moves | `mid` stored with each move; a repeat from the same seat changes nothing |
| No double results | `status` moves to `finished` exactly once. Every ending command, and every alarm, re-checks `status` first. `result` is written in the same transaction as `status`. |
| Ordered events | One socket preserves order. `rev` detects gaps across reconnects. Any doubt ends in `sync`, then a full `state`. |
| Client and server agree on the board | Same engine, same commit; `fen` in every `moved`; full replay on every `state` |

### 8.2 Race scenarios

| Scenario | What happens |
|---|---|
| Both players send something at nearly the same time | The object handles one, then the other. Only the side to move can move. Anything else (an offer, a resignation) is judged against the updated state. Example: Black resigns while White's move is in flight. Whichever arrives first wins. If the move arrived first, the resignation still ends the game after it. |
| A move is sent, the connection drops, the page doesn't know whether it landed | The page keeps its pending move in memory (`ply`, `uci`, `mid`). After reconnecting it gets `state`. If `moves[ply] === uci`, the move landed: confirm it. If `moves.length === ply` and it's still this player's turn, resend the same message with the same `mid`. Otherwise the game moved on: drop the pending move. Only the player to move can fill `ply`, so the first check is unambiguous. |
| Double click, or the same move sent twice | The UI accepts one move per turn and locks input while a move is pending. A second identical message has the same `mid`: no change. A second message with a different `mid` has a stale `ply`: rejected, and the page ignores it because its first move was already confirmed. |
| Reconnect while the server is processing a move | The new socket's `hello` waits for the move handler (input gate). Its `state` already includes the move. The old socket may also deliver `moved`, which `rev` marks as a duplicate. |
| A stale page sends a move from an old position | `ply` doesn't match: `rejected` (`stale`) plus `state`. The page drops its local move and redraws. |
| The game ends by an alarm while a player moves | Serial processing: whichever runs first wins. The loser sees `game-over` and the final `state`. |
| Two tabs of the same player | Both are authenticated sockets of one seat. A move from either is applied once; both get every event. |
| Opponent and alarm both end the game | Same as above: the first transition wins, and the second finds `status = finished` and does nothing. |

### 8.3 Disconnects and reconnects: exact behaviour

Timings are in `src/online/limits.ts` (§13).

**The client's reconnect loop:**
- tries at 0 s, then 1, 2, 4 and 8 s, then every 15 s, each with ±30% jitter;
- keeps trying as long as the page is visible and the game isn't finished;
- when the page is hidden, it pauses, and resumes at once on `visibilitychange` or `online`;
- shows "Reconnecting…" after 2 s, with a "Retry now" button;
- after 30 s without success, also offers to finish the position against the computer (the last row
  of the table below).

**The server's view of presence:** a seat is *present* while it has at least one authenticated socket.
When its last socket closes, the server records `absentSince` and broadcasts `presence`.
A dead connection that never sent a close frame (laptop asleep, network gone) is detected in one of two
ways:

- (a) Cloudflare's edge closes it after its idle timeout, which the client's pings normally prevent.
- (b) A **lazy liveness check.** Whenever the object handles any message, it compares the last
  heartbeat time of each of the opponent's sockets (`getWebSocketAutoResponseTimestamp`) with the
  current time. If one is more than 75 s old, the socket is closed, and `absentSince` is set to its last
  heartbeat.

The waiting player's page sends `sync` every 60 s once the opponent has been silent for 2 minutes, so
the check happens without a server timer. **The M0 spike measures how long (a) actually takes.**

| Situation | The returning player | The opponent sees | The game |
|---|---|---|---|
| Refresh (F5) | Page reloads, token from `localStorage`, `hello`, `state`, same position | Nothing: presence is debounced 5 s on screen | Unchanged |
| Tab or browser closed | Returns by the invite link or from history; the token is still there | After 5 s, "Opponent left the game"; at 120 s, **Claim win** and **Call it a draw** buttons, with a countdown before that | Stays active; nothing automatic |
| Laptop sleeps, phone locks | Reconnects on wake; a pending move is reconciled (§8.2) | Same as closed, once the absence is detected | Active |
| Network change (Wi-Fi ↔ mobile) | Socket drops, reconnects in ~1 s | Usually nothing | Unchanged |
| Brief Wi-Fi loss | A missing `pong` (10 s) triggers a reconnect; "Reconnecting…" after 2 s | At most a brief "Opponent reconnecting…" | Unchanged |
| Backend deploy | Platform closes every socket [S4]; both pages reconnect in 1–3 s | "Reconnecting…" briefly on both sides | Unchanged: everything is in storage |
| Returns after 10 s | Resumes | "Opponent is back" | Unchanged |
| Returns after 5 min | Resumes, or sees "White claimed the win after you left" | — | Unchanged, or finished by a claim |
| Returns after 30 min | Same as 5 min | — | Same |
| Never returns | — | Can claim from 120 s | Finished by the claim; if nobody claims, `abandoned` after 7 days without moves or connections; deleted 30 days later |
| Both players gone | — | — | Waits; abandoned after 7 days |
| Token lost (private window closed, site data cleared, another device) | Can't prove the seat: sees "This game is between two other players" | Can claim after 120 s | **Known v0.3 limitation** (no accounts). A "continue on another device" link that carries the token in the URL fragment is a v0.3.x candidate. |
| The game server can't be reached for 30 s (a Cloudflare incident, or a quota overrun the capacity guard failed to prevent) | Banner: "We've lost the connection to the game server. Your game is saved, and we'll keep trying." Buttons: **Keep waiting**, and **Finish this position against the computer**, which opens the local board at the same position against the computer (labelled, Auto level) | The same banner on their side | Saved on the server; resumes the moment it's reachable |

Clocks don't exist in v0.3, so nothing runs out while a player is away. With clocks (v0.4), the
absent player's clock keeps running (§10).

## 9. Online-only policies: rules questions for the founder

None of this changes `docs/RULES.md`: the rules of the game are untouched. These are platform
policies, of the same kind as "draw by agreement" or "resignation", needed only because the players
aren't at the same table. **The founder approved every recommendation below on 8 October 2026**
(F2–F4 in the master blueprint).

| # | Question | Recommendation | Why |
|---|---|---|---|
| R1 | May a player whose opponent has gone **claim the win** (or call a draw)? After how long? | **Yes, after 120 s of continuous absence**, the player's choice; never automatic | Untimed games otherwise hang forever. 120 s rides out refreshes, network changes and deploys. |
| R2 | May a game be **aborted** with no result? | **Yes, until both sides have made a move**, and by the creator while nobody has joined | Covers "joined and walked away" with nothing at stake |
| R3 | What happens to a game nobody touches? | **Abandoned** (no winner) after 7 days without moves or connections; deleted 30 days later | Storage and privacy hygiene |
| R4 | **Move limit**: the saved-game format allows 2,000 plies (`MAX_MOVES`) | **Draw at 2,000 plies** ("move-limit") | Keeps every online game exportable. The fifty-move and threefold rules end real games long before. |
| R5 | **Draw offers** online | Stand until answered or until the opponent moves; 3 per player per game | Standard online practice; stops spam |
| R6 | **Takebacks** online | **None in v0.3.** Local play keeps its undo. | Takebacks need consent, and that UI is a feature of its own. A request-and-accept takeback could come later. |
| R7 | **Flag fall** (clocks, v0.4) | **Running out of time always loses** | Standard chess draws when the opponent can't possibly mate, but Mean Chess has no insufficient-material draws: bare kings can still capture each other (D-13). So the opponent can always win, and a timeout is always a loss. |
| R8 | Threefold and fifty-move online | **Automatic, as offline (D-13)**: no claim needed | Unchanged rules; listed for completeness |
| R9 | What the board shows online | **Exactly what local play shows.** No Kill Zone hints, no "your opponent can win next move", royal wins look like captures (D-39, D-46); the result screen explains afterwards | Founder rulings; the server sends no analysis |

**Brief vs canonical rules.** The planning brief describes Royal Cannibalism as needing "no Royal
Capture". The canonical rules (RULES.md, D-04) say "no **royal move**", which also excludes Royal
Slaughter. The engine implements RULES.md, so nothing changes. Recorded so nobody "fixes" it.

## 10. Clocks: deferred to v0.4, specified now

**v0.3 has no clocks** (P2-07). Clocks add server time authority, flag detection by alarm, lag
handling, and interaction with disconnects. v0.3's job is reliable complete games.

But clocks must come **before** any public lobby (v0.5): strangers without clocks can stall forever.

v0.4 semantics, so that v0.3's data model leaves room:
- **Time controls:** none (as v0.3), or Fischer increment. Presets: 3+2, 5+3, 10+5, 15+10, 30+0, plus
  custom (1–60 minutes, 0–30 s increment). Correspondence (days per move) comes later.
- **Authority:** the server stores each side's remaining milliseconds and `turnStartedAt`. When a move
  arrives:
  1. `elapsed = now − turnStartedAt`;
  2. if `remaining − elapsed ≤ 0`, the mover's flag has fallen: loss (R7), and the move is not
     applied;
  3. otherwise the mover's clock becomes `remaining − elapsed + increment`.
- **Clock start:** each side's clock starts only after its first move. If White doesn't move within
  60 s of the game starting (or Black within 60 s of White's first move), the game is aborted. This is
  Lichess-style.
- **Flags with nobody moving:** an alarm is set for the moment the side to move runs out. When it fires,
  the object re-checks and ends the game (`timeout`, a new end reason).
- **Display:** the client counts down locally from the last event, corrected by `serverTime`. Timers
  in background tabs are throttled, but the display is cosmetic: the server decides.
- **Lag:** none at first. If players complain, add Lichess-style compensation, capped (for example up
  to 300 ms per move from the measured round trip). That would be a v0.4.x decision.
- **Disconnects:** the absent player's clock keeps running. The claim rule (R1) still applies.

## 11. Chat and social features in v0.3

| Feature | v0.3? | Reason |
|---|---|---|
| Text chat | **No** | Needs moderation, reporting and blocking; it is a children's-safety and abuse surface; and v0.3 players are friends who already have a chat app |
| Emoji reactions, preset messages | No (v0.4+ candidate: "Good game", "Well played", "Rematch?") | Nice, not core. Preset phrases avoid moderation. |
| Display names | No: "You" and "Opponent" | Names are user text, and so a moderation surface. They arrive with the lobby. |
| Rematch | **Yes** | The core loop: finish, rematch, keep playing |
| Copy invite link, share sheet | **Yes** | How games start: `navigator.share` on phones, copy elsewhere |
| Share a finished game | **Yes**: the same link shows the finished game read-only for 30 days | Turns memorable games (a Royal Slaughter) into something to show people |
| Friend requests, profiles | No | Need accounts |
| Live spectators | No (v0.5, with the lobby) | More sockets and more rules; nobody needs it yet |

## 12. Versions and compatibility

- `PROTOCOL_VERSION = 1`. The server accepts the current and the previous version (P2-15). An older
  client is rejected with `unsupported-protocol`, and the page offers a reload.
- Changes inside a version are additive only: new optional fields and new event types, which old
  clients ignore.
- `rules` must equal the game's rules version. Every game created under Rules v0.1 is played to the end
  under Rules v0.1.
- The `build` (git sha) is in `/v1/health` and in logs, not in the protocol.

## 14. What the player sees (screen states)

| State | Screen |
|---|---|
| `/online/` with no game | **Create a game** (choose White, Black or random) and **Join with a code** |
| Creator waiting | The invite link with **Copy** and **Share**, the code in large type (`7KQ2M-X9FTA`), "Waiting for your friend…", **Cancel invite** |
| Invitee arrives | "You've been challenged to Mean Chess. You'll play Black." The three key rules (the existing quick rules), a tutorial link (opens in a new tab), and **Join game** |
| Playing | The existing board and side panel. "Your move" or "Their move"; draw offer and answer; resign; abort while allowed |
| Opponent away | Banner: "Opponent left the game", with a countdown to **Claim win** or **Call it a draw** |
| Reconnecting | Banner after 2 s: "Reconnecting…" and **Retry now**. Input is locked; the board stays visible. |
| Finished | The existing result dialog, plus **Rematch**, **Share this game** and **New game** |
| Online full for today | "Online play is full for today. It reopens in 3 h 20 min (00:00 UTC). Games already started aren't affected, and invites you've sent still work." **Play the computer** (Auto level, labelled) and **Play a friend on this device**. Not an error. |
| Errors | Not found or expired; "between two other players"; outdated (reload); online play paused (kill switch): "play the computer meanwhile" |
